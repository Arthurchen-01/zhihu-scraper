# 功能路线与后续待办清单

> 状态：2026-07-26 已确认路线图
> 说明：本文件只记录产品范围、重建顺序和暂未实施的功能，不代表当前代码已经支持。

## 1. 项目定位

- 第一目标：做成可用于腾讯实习展示的工程化项目，功能真实可用、测试充分、容易解释。
- 第二目标：满足个人长期归档与检索知乎内容的需要。
- 使用者：
  - 熟悉命令行、希望学习项目架构的开发者。
  - 不熟悉命令行、希望由 Codex 等 Agent 代为操作的普通用户。
- 重建策略：在当前仓库和 `main` 分支上受控重建；不保留旧接口兼容层。新实现覆盖并验证旧能力后，再删除对应旧模块。
- 提交策略：按可运行、可测试、可解释的小闭环持续提交，而不是把一次改动机械拆成无意义提交。

## 2. 必须支持的抓取范围

- [ ] 单篇专栏文章
- [ ] 单个回答
- [ ] 问题下的多个回答
- [ ] 整个专栏
- [ ] 专栏文章所属专栏信息
- [ ] 一级评论与二级回复
- [ ] 独立知乎视频（`zvideo`）
- [ ] 正文图片
- [ ] 动图
- [ ] 数学公式
- [ ] 代码块、引用、列表、表格和超链接

当前明确不做：

- 专栏合集
- 文章或回答中的内嵌视频
- 作者主页及其全部内容
- 搜索结果抓取
- 想法、收藏夹、盐选等其他内容

## 3. 输出范围

- [ ] Markdown：面向阅读和长期归档。
- [ ] HTML：由归一化后的内容数据生成静态页面，不复制知乎的 HTML、CSS 或 JavaScript。
- [ ] SQLite：第一阶段保存结构化内容、评论、媒体和来源关系。
- [ ] 媒体文件：图片、动图、独立视频、公式渲染所需资源。
- [ ] PDF：选做，默认关闭。

不提供面向用户的原始 JSON 归档格式。程序内部使用 JSON 传递数据不属于用户输出格式。

## 4. 专栏归档与文章页

知乎文章与专栏是多对多关系：同一篇文章可能同时被多个专栏收录。因此需要区分：

- `收录专栏`：文章实际关联的全部专栏。
- `本次归档自`：用户本次指定抓取的专栏。

文章顶部只展示紧凑元信息，不把几十篇目录全部堆在正文前：

```text
作者 · 发布时间 · 知乎原文
收录专栏：专栏 A、专栏 B
本次归档自：机器学习 · 本栏目共 81 篇 · 查看完整目录
```

不使用 `index.md` 或 `index.html`。只有“整个专栏”使用以下批量目录结构：

```text
知乎归档/
├── zhihu.db
└── 机器学习/
    ├── 机器学习.md
    ├── 机器学习.html
    ├── 内容/
    │   ├── 一文归纳AI数据增强之法.md
    │   ├── 一文归纳AI数据增强之法.html
    │   └── ...
    ├── media/
    └── assets/
```

- `机器学习.md` 和 `机器学习.html` 是专栏说明与完整目录。
- `内容/` 只用于保存整个专栏中的文章。
- `media/` 保存正文图片、动图、视频和其他媒体。
- `assets/` 仅在生成 HTML 时保存共用 CSS、JavaScript 和公式渲染资源。
- `zhihu.db` 位于归档根目录，由全部归档内容共用。

单篇文章、单个回答、问题下多个回答和单个视频都使用精简结构：

```text
标题/
├── 标题.md
├── 标题.html
├── media/
└── assets/
```

- 单个回答的文档只包含指定回答。
- 问题下多个回答时，多个回答作为不同章节合并到同一个 `问题名.md` 和 `问题名.html`，不创建 `内容/`。
- 文件名优先使用可读标题；遇到同名、系统保留名称或过长标题时才追加知乎 ID 或安全截断。
- 没有媒体或 HTML 资源时，不创建空的 `media/`、`assets/`。

专栏/问题同名文件提供：

- [ ] 专栏标题、简介、作者、抓取时间和抓取时文章总数
- [ ] 按年份分组的完整文章目录
- [ ] 文章页返回目录
- [ ] 上一篇与下一篇导航
- [ ] 原始知乎链接

## 5. 评论策略

- [ ] 评论抓取功能默认关闭。
- [ ] 开启后，每个内容按知乎接口实际返回顺序抓取前 10 条一级评论；不足 10 条时全部抓取。
- [ ] 每条一级评论抓取最多 10 条二级回复；不足 10 条时全部抓取。
- [ ] 批量抓取整个问题或专栏时，对每个内容执行同一规则。
- [ ] 保存评论层级、作者、时间、点赞数、原始标识、归属内容和接口排序来源。

待验证：知乎不同内容类型的评论接口采用何种排序。程序不把接口返回顺序伪造成“热门”或“点赞”排序。

## 6. 视频与媒体策略

- [ ] 独立 `zvideo` 下载最高可获得清晰度，不额外询问用户。
- [ ] 保存原始链接、媒体元数据和本地文件路径。
- [ ] 支持断点续传、重试和完整性校验。
- [ ] 同一媒体被不同归档引用时允许保留多份；后续再决定是否提供去重选项。
- [ ] 图片、动图和视频统一视为媒体资产，由同一媒体层管理。
- [ ] 数学公式保留原始表达，并可在 Markdown/HTML 中正确显示。

## 7. HTML 方案

HTML 是程序根据抓取后的内容重新生成的阅读页面，不是从知乎复制“前端三件套”。

第一阶段采用静态前端：

- HTML：语义化正文、元信息和目录。
- CSS：项目自有的阅读样式，作为本地资源保存。
- JavaScript：只承担目录折叠、主题切换、复制代码等轻交互。
- 公式：使用本地 KaTeX 或 MathJax 资源渲染。

第一阶段不引入 React、Vue 或单独的前端构建系统。只有当交互复杂度确实需要时再评估。

## 8. 后续待办：本地搜索

本阶段不实现关键词搜索或语义搜索。先完成抓取、归一化、Markdown、HTML、SQLite 和媒体闭环。

### 关键词搜索

- [ ] 使用 SQLite FTS5 建立全文索引。
- [ ] 标题、作者/专栏、正文、评论采用不同权重。
- [ ] 支持内容类型、作者、专栏和时间过滤。
- [ ] 返回命中片段并高亮关键词。
- [ ] 对一至两个汉字的短查询提供精确匹配或 `LIKE` 回退。

不需要本地模型、远程 API 或联网。

### 语义搜索

- [ ] 按标题、段落和章节切分内容，不破坏公式与代码块。
- [ ] 使用本地中文向量模型生成嵌入。
- [ ] 默认候选模型：`BAAI/bge-small-zh-v1.5`。
- [ ] 第一次使用时下载模型，之后可离线运行。
- [ ] 保存模型名、版本、向量维度和切分器版本，以支持可重建索引。
- [ ] 关键词结果与向量结果做混合排序。
- [ ] 本地模型不可用时清楚提示并回退到关键词搜索。
- [ ] 可选支持远程嵌入 API，但不作为默认路径，密钥只从环境变量读取。

语义搜索需要“把文字转换为向量”的模型。默认本地运行时不需要用户购买 API；远程 API 只是可选加速或替代方案。

## 9. 后续待办：知识图谱

本阶段只在 SQLite 中保存将来可能使用的稳定实体和来源关系，不实现知识图谱查询或可视化。SQLite 是一个本地数据库文件，用户不需要直接阅读或手写 SQL。

建议的核心实体：

- 内容：文章、问题、回答
- 人物：作者、评论者
- 容器：专栏
- 互动：一级评论、二级回复
- 资产：图片、动图、视频
- 搜索：文本块、全文索引、向量

### 确定性关系图

先保存能够从知乎原始数据直接确认的关系：

- [ ] 文章 `收录于` 专栏
- [ ] 回答 `回答了` 问题
- [ ] 内容 `由……创作` 作者
- [ ] 内容 `拥有` 评论
- [ ] 评论 `回复` 评论
- [ ] 内容 `包含` 媒体
- [ ] 内容 `链接到` 其他已归档内容

这些关系不需要大模型，可测试、可解释、可追溯。

### 关系可视化

- [ ] 在单篇内容附近展示小范围关系网络，而不是一次加载整个数据库。
- [ ] 默认限制约 50 至 100 个节点，并允许按关系类型筛选。
- [ ] 评估使用 Sigma.js 等轻量可视化库。

### 语义知识图谱

- [ ] 评估从正文中抽取人物、概念、方法和论证关系。
- [ ] 大模型抽取出的关系必须记录来源片段、模型、版本、时间和置信度。
- [ ] 推断关系必须能整体删除并重新生成，不能与确定性关系混淆。

第一版不引入 Neo4j，不持久化“内容相似”边；相似关系在查询时通过向量计算。

## 10. 浏览器、请求策略与代理

- [ ] 优先使用轻量 HTTP/API 抓取。
- [ ] 遇到登录态、签名、反爬或字段缺失时，回退到持久化浏览器会话。
- [ ] 可选通过 CDP 连接用户已经登录的 Chrome。
- [ ] 在 HTTP 与浏览器之间同步必要 Cookie，并通过登录状态接口验证会话。
- [ ] 把随机等待重构为明确的请求策略：并发数、请求间隔、退避、重试和抖动。
- [ ] 代理作为可选传输配置，默认关闭；日志不得泄露 Cookie、账号或代理凭证。

不把“模拟真人”作为承诺；项目目标是限速、稳定和尊重站点负载。

## 11. 三个平台的真实支持

业务逻辑可以共用，但操作系统在浏览器安装、路径、文件名、进程管理和原生依赖方面不同。启动时只判断一次平台，再把平台差异分发给 Windows、macOS 或 Linux Adapter；抓取和渲染模块不应散落系统判断。

- [ ] 保留项目独立虚拟环境，避免依赖污染用户的系统 Python。
- [ ] 使用 `pyproject.toml` 声明依赖，并提交锁文件保证三平台安装可复现。
- [ ] 区分基础抓取依赖、浏览器依赖和开发测试依赖；普通用户不必安装开发工具。
- [ ] 同时提供适合普通用户的安装命令和适合开发者的 `uv` 工作流。
- [ ] GitHub Actions 同时覆盖 Windows、macOS、Linux。
- [ ] 三个平台验证安装、命令入口、路径处理和 SQLite 基础保存。
- [ ] 为 Windows 提供 PowerShell 安装入口。
- [ ] 处理 Windows 保留文件名、路径长度和打开文件重命名差异。
- [ ] 浏览器安装和发现按平台实现并测试。
- [ ] 低频执行真实 Playwright 启动测试。
- [ ] 只保留一个受控的知乎在线烟雾测试，其余使用固定测试数据。
- [ ] 启动时检测浏览器和运行依赖，并给出可理解的降级提示。

“README 中写了三个系统可用”不等于三个系统已经经过验证。

- [ ] 建立新的干净核心和稳定领域模型。
- [ ] 固定第一阶段主流程：知乎数据 → 归一化内容模型 → Markdown 渲染器 / HTML 渲染器 / SQLite 保存器。
- [ ] 抓取、归一化、渲染、媒体、存储、运行平台与浏览器会话之间使用明确接口。
- [ ] 每迁移一个可运行能力，就补对应单元测试和最小集成测试。
- [ ] 新实现通过测试后，删除该能力在旧位置的实现，包括旧文章抓取代码。
- [ ] 删除旧兼容层。
- [ ] 删除 OpenAI 翻译功能及相关依赖。
- [ ] 删除国际化运行逻辑，但保留并维护 `README_EN.md`。
- [ ] 清理过时的项目内 Agent Skills；最终仅保留简洁的 `AGENTS.md`、架构说明、路线图和真实测试。
- [ ] 删除未实现且容易误导的“多平台移植”产品设想，真实支持以测试矩阵为准。

## 13. 已确认与待讨论的默认值

已确认：

- Markdown：默认生成
- HTML：默认生成
- SQLite：默认启用，整个归档库共用根目录下一个 `zhihu.db`
- 评论抓取：关闭
- 评论数量：开启后每个内容最多 10 条一级评论，每条最多 10 条二级回复
- PDF：关闭
- 原始 JSON 输出：不提供
- 视频：最高可获得清晰度、断点续传、保存原始链接
- 代理：关闭
- 不保留旧接口兼容层

- 整个专栏/问题批量抓取时，媒体下载是否默认启用
- Cookie 的保存位置、加密方式、过期检测和重新登录体验
- 配置文件中哪些选项应展示给普通用户，哪些应保持为内部工程参数

已延期：

- 关键词搜索
- 语义搜索

## 14. 第一阶段实施顺序

1. 定义领域模型、抓取结果合同和目录结构。
2. 建立文章、回答、问题、专栏和独立视频的 URL 路由。
3. 打通一篇文章的抓取、归一化、Markdown/HTML/SQLite 保存闭环。
4. 补图片、动图、公式和独立视频媒体层。
5. 扩展到单回答、问题多回答和整个专栏。
6. 加入可选的 10/10 评论抓取。
7. 完成 Windows、macOS、Linux 的安装和测试矩阵。
8. 清理已经被替代的旧模块、兼容层和项目内 Agent Skills。

关键词搜索、语义搜索和知识图谱在上述闭环稳定后另行排期。
